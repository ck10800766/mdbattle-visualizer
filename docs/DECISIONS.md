# Architecture Decision Records (ADR) & Design Log

本文件記錄 `mdbattle-visualizer` 核心架構決策與邏輯演進歷史，避免未來維護或重構時發生「A 改 B、後來又改回 A」的循環修改。

---

## ADR-001: 連擊（Combo）身體定位與回原位規則 (Combo Positioning & Return-to-Origin)

### 背景 (Context)
早期版本中，`lookaheadComboState` 將「連擊數累計 (`isNextFrameSameCombo`)」與「角色是否回到原位 (`shouldReturnToOrigin`)」過度耦合且加入嚴格的 `skillId` 相等比較。這導致多段連招（如迪盧克逆焰之刃 `diluc_onslaught_1/2/3`、普通攻擊 `diluc_sword_1/2/3/4`）因後綴不同被誤判為「不同技能」，造成角色每一擊都跑回原點重新衝刺。
同時，先前的前瞻邏輯忽略了場景旁白（`isSceneNarrationFrame`）、擲骰檢定（`diceCheck`）與一般文本，導致角色在連擊途中遇到 1~2 秒的劇情旁白時，依舊維持在目標臉上（`stayAtTarget = true`），產生「角色黏在目標身上」的視覺 Bug。

### 決策 (Decision)
1. **核心原則：同回合、同目標且無中斷的連擊，角色一律停留在目標前連續攻擊，不回到原位。**
   - 只要同一攻擊者在同回合內連續對同一目標發動單體攻擊（無論是同技能多段 `_1/_2/_3` 還是連續普通攻擊），角色即在目標身前連續揮擊（`stayAtTarget = true`），直至連擊結束才瀟灑後撤。
2. **必須後撤回原位（`shouldReturnToOrigin = true`）的中斷條件：**
   - **切換為 AOE 技能**（`lookahead.isAOE`）：需回原位或移至舞台中央發動全場攻擊。
   - **切換攻擊目標**（`lookahead.targetId !== frame.targetId`）：需位移至新目標。
   - **非戰鬥停頓事件**：
     - 場景旁白橫幅（`isSceneNarrationFrame`）
     - 擲骰／占卜／幸運檢定（`diceCheck`、`占卜判定`）
     - 隊友或自身施法、治療（`HEAL`、`SP_RECOVER`）
     - 召喚登場（`SUMMON`）
     - 幸運掉落物砸頭（`LUCK_EVENT`，避免與目標重疊受傷）
     - 反擊推開／中斷（`COUNTER`）
3. **場景旁白安全防護**：
   - 於 `stage.js` 的 `isSceneNarrationFrame` 渲染時，主動清除所有作戰單位的暫態位移動畫（除結婚格擋持有外），確保旁白播放期間全員必定回到標準陣型。

## ADR-002: 通用召喚物退場語義解析 (Universal Semantic Summon Despawn)

### 背景 (Context)
先前的 `SUMMON_DESPAWN_REGEX` 只寫死了沉睡騎士的「揮了揮手，回到.+?的隊伍裡」與「離開了戰場」，遇到克萊恩的歷史投影（「輪廓一點一點淡去，散回了灰霧裡」）無法辨識，導致召喚物在退場後仍留在舞台上成為幽靈單位（GitHub Issue #20）。

### 決策 (Decision)
1. **禁止針對特定角色或技能寫硬編碼偵測**。
2. 改採**通用語義特徵正則**，涵蓋自然消散、時間結束、解召、返回等通用動詞：
   `/(?:淡去|散回|散去|消散|消逝|消失|退場|離場|脫離戰場|離開(?:了?戰場)?|離去|撤退|隱沒|揮了揮手，回到|回到.+?(?:隊伍|身邊|身旁|空間|法陣|歸處|冥界|灰霧|陰影|原處|手牌|卡組|召喚)|返回.+?(?:隊伍|身邊|身旁|空間|法陣|冥界|界)|化(?:作|為).*(?:白煙|青煙|黑煙|煙霧|塵埃|光點|虛無|泡影|灰燼)|時間(?:結束|已到|用盡|到了)|解除.*召喚|召喚.*解除|召喚結束)/`
3. **多欄位實體解析**：依序由 `log.actorId`（主動離場的召喚物）、`log.targetId`（被解召的目標召喚物）與在場召喚物名稱文本匹配，精確定位退場實體。
4. **防止退場文本觸發敘事登場**：若伺服器在副本結束時對未登場的預載實體發出退場日誌，`SUMMON_DESPAWN_REGEX` 會攔截敘事自動登場，避免產生虛假的「🌀 召喚登場」標記。

## ADR-003: 版本號管理與使用者端可見性 (Version Management & UI Visibility)

### 背景 (Context)
先前多個 PR 迭代皆未推進 `package.json` 中的版本號，導致 Tampermonkey / Violentmonkey 無法偵測到更新，使用者回報 Issue 時也無從得知實際運行的補丁版本。

### 決策 (Decision)
1. 每次功能或修復 PR 均需遵循語意化版本（SemVer）推進 `package.json` 與 `src/constants.js`（`APP_VERSION`）。
2. `build.mjs` 自動將完整版本注入 Userscript `@version` 標頭。
3. 在舞台控制列右側顯示醒目而低調的版號標籤（`vX.Y.Z`），讓使用者截圖或回報時能即時確認當前加載的確切版號。

## ADR-004: 召喚物邊緣進出場動畫 (Screen-Edge Summon Animations)

### 背景 (Context)
當舊召喚物退場後緊接著下一隻同名或同外觀召喚物進場時（例如克萊恩連續拉出「有紀的歷史投影」），原地的縮放淡入淡出容易讓使用者誤以為同一隻角色在閃爍。

### 決策 (Decision)
1. **左側我方召喚物**：自螢幕左側外緣（`translateX(-180px)`）帶淡藍光暈滑入戰場；退場時向左側邊緣滑出淡出。
2. **右側敵方召喚物**：自螢幕右側外緣（`translateX(180px)`）帶灰霧緋紅光暈滑入戰場；退場時向右側邊緣滑出淡出。
3. 確保召喚進退場影格給予至少 `650ms` 展示時長，使連續換人具備明確的「向外退場、自外入場」方向軌跡。

## ADR-005: 護盾狀態與狀態列排版架構 (Shield & Status Tray Layout)

### 背景 (Context)
原本角色血條高度有限且四周有傷害跳字與連段統計。如果將 Buff/Debuff 圖示硬塞在血條下方或置中，會與血量文字互相遮擋；若在血條內部硬擠一條細護盾條，容易在受到大額傷害時產生鋸齒或不易看清。

### 決策 (Decision)
1. **狀態列外置於頭像側邊**：
   - 左側角色狀態列靠頭像左方（`right: calc(100% + 6px)`）。
   - 右側角色狀態列靠頭像右方（`left: calc(100% + 6px)`）。
   - 垂直由上至下排列，與血條完全脫鉤，確保血量動態清晰可見。
2. **護盾採用卡片發光外框 (`shield-active`)**：
   - 當單位持有有效護盾或防護罩時，卡片容器邊框呈現水藍色呼吸光暈（`border-color: #63b3ed; box-shadow: 0 0 8px #63b3ed`），直觀而不佔用內部排版空間。
3. **多重狀態交替閃爍光暈**：
   - 當角色身上有多個 Buff/Debuff 時，頭像輪廓採用漸層交替閃爍色光，提示玩家該單位帶有多重特殊增減益效果。

## ADR-006: 離線戰報可攜性與血量內聯 (Offline Report Portability & HP Inlining)

### 背景 (Context)
伺服器回傳的文字戰報（`logs[]`）本身往往缺少 `participants` 陣列（包含各角色初始最大血量 `hp.max` 與頭像網址）。當前腳本雖能在線上透過 API 平行補齊，但如果使用者下載原始戰報 JSON，在離線或伺服器紀錄過期後載入，血量校正將失去基準。

### 決策 (Decision)
1. 在 `reportIO.js` 執行 `exportCurrentBattleReport` 時，必須將執行期已校正與補齊的 `engineState.actors` 資料**內聯封裝至 JSON 頂層的 `participants` 陣列**。
2. 匯出的戰報檔名規範為 `mdbattle-<leftRep>-vs-<rightRep>-<timestamp>.json`，方便玩家歸檔與辨識。
3. 脫機載入時優先讀取內聯的 `participants`，達成 **100% 離線免連網完整回放**。

## ADR-007: 嚴格無頭黃金快照回歸測試 (Headless Golden Snapshot Testing)

### 背景 (Context)
戰鬥視覺化涉及複雜的正則解析、回合推論、多段連段預判、血量回推與狀態機。任何一行程式碼修改（如前瞻判斷或正則微調）極易引發非預期的連鎖副作用，而在瀏覽器中手動測試 500 幀戰報極為費時且容易遺漏。

### 決策 (Decision)
1. **脫離瀏覽器環境的純 Node.js 快照管線**：
   - 透過 `scripts/snapshot-runner.mjs`，在不啟動瀏覽器的情況下直接執行 `parseParticipants`、`buildStateSnapshots`、`simulateRuntimeTrace` 與 `extractTimelineMarkers`。
2. **ES6 集合正規化序列化**：
   - 透過 `toSerializable` 將 `Map` / `Set` 依 Key 字母排序轉化為確定性的純 JSON，杜絕物件迭代順序造成的偽陽性差異。
3. **提交前一致性檢查門禁 (`npm run check`)**：
   - 自動串聯快照測試、`esbuild` 打包與 `git diff --exit-code dist/`，並整合於 GitHub Actions CI，確保任何 PR 都不會帶入回歸破壞或未編譯的成品。

## ADR-008: 堅持視覺回放本位，拒絕數據臃腫化 (Visual Playback Over Bloated Statistics)

### 背景 (Context)
社群中已有其他專門從事戰報深層數據挖掘與試算表統計的插件（如 `mydoujin-battle-stats`）。若 MDBV 也跟著實作技能傷害佔比、命中/暴擊率圓餅圖、每回合輸出曲線等繁複圖表，不僅會讓腳本體積平白膨脹、排版擁擠，更會模糊 MDBV「2D JRPG 動態沉浸式戰鬥劇場」的核心定位。

### 決策 (Decision)
1. **劃清功能邊界，不抄襲、不取代專門統計插件**：
   - 複雜的暴擊率迴歸、技能佔比長條圖與試算表數據留給專門的統計外掛處理。
2. **核心要求僅限「傷害與承傷數值計算精確」**：
   - 結算面板（MVP）維持 JRPG 經典極簡風格（總輸出／總承傷）。
   - 確保數值計算滿足「生命守恆」（有效輸出加總嚴格等於敵人損失血量 + 回血量，不虛高、不失真，已於 PR #15 落實）。
3. **重心始終放在「純畫面演出與打擊流暢度」**：
   - 資源全數集中在打磨角色技能演出、連段節奏、動畫銜接、站位位移與視覺沉浸感，不做過度數據化。

## ADR-009: 召喚物生命週期、致命陣亡離場與多階段重生解析 (Summon Lifecycle, Fatal Death Departure & Multi-Phase Revivals)

### 背景 (Context)
在保護傘公司（Umbrella Corp, 召喚獵殺者、暴君、舔食者、追跡者共 10 隻召喚物）與瘟疫公司（影分身陣亡後再次召喚）的複雜戰報中，召喚物與重生機制存在三大結構性問題：
1. **陣亡召喚物未退場致使舞台擁擠**：先前僅依賴 `SUMMON_DESPAWN_REGEX` 偵測「化為白煙」、「淡去」等主動離場文本。戰鬥中被打倒（`DEATH`）且不再重生的召喚物永遠留在畫面上，導致後期敵方隊列堆疊多達 10 隻卡片擠爆畫面，且 ATB 軸塞滿已陣亡圖標。
2. **重生語意偵測不足**：追跡者三階段重生（「膨脹成一團蠕動的血肉，四肢著地爬了過來」）未被既有正則捕捉，導致三階段未被校準器分段，血量推算異常。
3. **重生後死亡狀態未解除**：單位重生時 `actorsDeathState` 未被設為 `false`，導致後續增益被封鎖，且後續再次陣亡時因 `alreadyDead = true` 而遺漏死亡事件、特寫與里程碑標籤。

### 決策 (Decision)
1. **前瞻掃描未來重生區間 (`hasFutureRevival`)**：
   - 若召喚物陣亡後在後續日誌中存在重生事件（如暴君 T-00、追跡者），則保留於戰場倒地狀態，等待手指抽搐與站起演出。
   - 若召喚物無未來重生事件（如獵殺者、舔食者、影分身），則在陣亡動畫及關聯敘事文本（如掉落綠色藥草、補給箱）完成後觸發 `isDespawnEvent` 平滑退場（邊緣滑出淡出），避免同名召喚物重疊或卡片過度堆疊。
2. **泛用多階段重生語意擴充**：
   - 正則納入「爬了過來」、「蠕動的血肉」、「再次站起」、「傷口全部合上」等各類 Boss/召喚物三階段特徵，支援任意多階段實體。
3. **動態階次標記**：
   - 里程碑時間軸依同一實體的重生次數，動態標註「🔥 二階段甦醒」、「🔥 三階段甦醒」、「🔥 四階段甦醒」。
4. **重生與主動行動雙重解死防護**：
   - 遇到重生文本或角色主動攻擊/施法時即時解除死亡狀態，確保多階段實體的每一次陣亡皆能完整觸發 Fatality 特寫與時間軸死亡釘。
